# Milestone 1, Step 1.9 (backend) — Push for messages — verification

Date: 2026-10-11. Run with `npx ts-node src/scripts/verify1_9_push.ts` (temporary
script, deleted after this file was written).

## What was built
- `backend/src/routes/mart/threads.ts` (extended) — `notifyNewMessage()` and
  `upsertMartMessageNotification()`, called (fire-and-forget, after the response is
  already sent — "never block the request") from both `POST /mart/threads` (the first
  message) and `POST /:threadId/messages` (every message after).
  - Always creates/updates the `AppNotification` row regardless of the recipient's
    `mart_message` preference (`02-data-model.md` §7.1: "Always create the in-app row;
    the pref only controls the push"); `sendPush` is only called when
    `prefs.mart_message` is true.
  - "One row per thread": if an **unread** `mart_message` row already exists for this
    exact thread (matched on the `linkTo` JSON text, which this file always builds the
    same way), that row's `title`/`body`/`createdAt` are updated in place instead of a
    new row being created — a burst of messages collapses into one notification. Once
    that row is marked read (via `POST /:threadId/read`, also extended this step to
    mark the matching `AppNotification` rows), the *next* new message correctly starts
    a fresh row rather than resurrecting the read one.
  - Title = the sender's `publicName()`; body = the message text capped to 80 chars,
    both per `02-data-model.md` §7.1's `mart_message` row.
- `mobile/src/screens/NotificationPrefsScreen.tsx` (extended), `en.ts`/`si.ts`
  (extended) — 3 new switches ("Messages and Offers", "New Requests Near You", "New
  Reviews") for `mart_message`/`mart_wanted`/`mart_rating`, the pref keys Step 0.3
  already added to `NOTIFICATION_PREF_DEFAULTS`. `mart_wanted`/`mart_rating` have no
  real trigger yet (Wanted posting is Milestone 2 Step 2.1, Ratings is 2.5) — the
  switches exist now per `03-api.md` §23 point 21's explicit instruction, ahead of the
  features that will use them, same as other backend-ahead-of-UI pieces this build.
- `mobile/App.tsx` — a new `martThread` branch in the existing notification-tap
  `onNavigate` handler (same `focusBookingId`-style prop + "handled" callback pattern
  already used for Garage/Vehicle Dashboard deep links), wired through to
  `MartNavigator`'s new `focusThreadId`/`onFocusHandled` props, which push straight to
  the thread screen on mount.

## An important, deliberate side effect — not a bug
`mart_message` rows are created in the **same, shared** `AppNotification` table the
app's existing (non-Mart) Notifications screen and its unread bell already read with
**no type filter** — `03-api.md` §9 only promises the existing `/notifications` *route*
stays untouched (unmodified code), not that Mart rows are invisible to it; Mart's own
filtered notification center (`GET /mart/notifications`, `mart_` types only) is
explicitly Milestone 2 Step 2.9, not built yet. Until then, **a Mart message a beta
tester receives will also show up in their main app's Notifications list and can light
up the main Vehicles-tab bell.** This is naturally self-limiting for now: a Mart thread
can only exist between two people who both have Mart access, since you can only receive
a `mart_message` about a listing you yourself posted (which requires passing the beta
gate). Flagged clearly to Vikum rather than only in this file, since it's a visible
behavior change to an existing, shared screen.

## Verification method
15 checks against a minimal standalone Express app (fake auth middleware switchable
between a buyer and seller phone, only the threads router mounted, ephemeral port —
never the real `index.ts`). Used polling (not a fixed sleep) to wait for the
fire-and-forget notification write to land, since it runs detached after the response
and a fixed delay would either be flaky or needlessly slow against Neon's real network
latency. Confirmed: opening a thread creates exactly one `mart_message` row for the
seller with the buyer's public name as the title and the message as the body, starting
unread; a second unread message in the same thread updates that same row's text rather
than creating a second one; marking the thread read also marks the notification read;
a message sent *after* that read correctly starts a brand-new row. Cleaned up every
notification, message, thread, listing and both temporary users, then confirmed all
affected tables' row counts were unchanged from before the test.

**Not verified by this script (deliberately, explained inline)**: whether `sendPush`
is actually skipped when `prefs.mart_message` is `false` — the recipient was never
given a real-looking Expo push token in this test (so `sendPush` would short-circuit
before any network call either way), avoiding a live call to Expo's push API during an
automated check. The `if (prefs.mart_message)` gate around that call is a one-line,
directly-readable condition in `threads.ts` — confirmed correct by reading the code,
not by a runtime assertion.
