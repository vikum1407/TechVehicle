# Milestone 1, Step 1.8 (backend) — Chat — verification

Date: 2026-10-11. Run with `npx ts-node src/scripts/verify1_8_threads.ts` (temporary
script, deleted after this file was written). This is the biggest backend surface of
Milestone 1 — 7 endpoints across threads and messages.

## What was built
`backend/src/routes/mart/threads.ts` (new router, mounted at `/mart/threads`), per
`03-api.md` §8:
- `POST /` — opens (or, idempotently, re-finds) a thread for `(listingId, caller)`,
  creating the first message atomically with the thread. Rejects the listing owner
  messaging themself (400), a sold/fulfilled listing (409 `LISTING_CLOSED`), a
  removed/missing listing (404), and a blocked relationship (403 `BLOCKED`).
- `GET /` (inbox) — `role=all|buying|selling`. Two things Prisma can't express as a
  single `where` filter are computed in application code instead: visibility (02
  §3.4's "closed time = the **earlier** of `removedAt` and `closedAt`" — comparing two
  possibly-null dates) via the exported pure `isThreadListingVisible()`, and the
  blocked-pair exclusion (which side is "the other person" varies per row, so it can't
  be a static field filter). Role resolution is the exported pure `roleFor()`. A
  removed listing's title/thumbnail fall back to the snapshot taken at thread creation;
  a still-active (even if sold) listing shows its current, live title/thumbnail.
- `GET /unread-count` — same visibility/blocked/hidden filters as the inbox, counting
  threads where `lastMessageSenderPhone != me` and `lastMessageAt > myReadAt` (or
  `myReadAt` is null) — the exact "unread thread" computed value from `02-data-model.md`
  §6.
- `GET /:threadId` — full thread detail + a cursor-paginated page of messages (30 per
  page, newest-first, matching spec). Deliberately has **no read-marking side effect** —
  that's `POST /:threadId/read`'s job alone, per the spec's explicit note. `deal`/
  `canRate`/`dealBanner` are computed from the real `dealState` column rather than
  hardcoded, so they'll start working correctly the moment Mark Sold (Milestone 2 Step
  2.4) and Ratings (2.5) exist — right now `dealState` is always null, so they're always
  null/false, but for a real structural reason, not a stub.
- `POST /:threadId/messages` — validates length (02 §4.2), rejects a closed/removed
  listing (403 `LISTING_CLOSED`) or a blocked pair (403 `BLOCKED`), updates the thread's
  preview fields, and un-hides the thread for the **recipient only** (not the sender) —
  so a thread one side deleted reappears for them the moment the other side replies.
- `POST /:threadId/read` — sets my own `...ReadAt`, and also marks matching
  `mart_message` notifications read (a correct no-op today since no `mart_message` rows
  can exist until Step 1.9 creates them — implemented now so that step needs zero
  changes to this file).
- `DELETE /:threadId` — one-sided hide, idempotent.

## Decision: deferred to Step 1.9, not this step
Creating `mart_message` `AppNotification` rows and sending push on a new message is
explicitly Milestone 1 Step 1.9's own deliverable per the build plan ("mart_message
notification + push... Push for messages"), so `POST /` and `POST /:threadId/messages`
both send a message successfully but create no notification row yet — logged in
`DECISIONS-MADE.md`.

## Verification method
41 checks: 8 pure-function checks (`isThreadListingVisible`'s earlier-of-two-dates rule,
including the tricky "closed 10 days ago, removed 1 day ago — still invisible" case; all
4 `roleFor` combinations) with no DB, plus 33 real HTTP-level checks against a minimal
standalone Express app (fake auth middleware that can be switched between a buyer and
seller phone mid-test, only the threads router mounted, ephemeral port — never the real
`index.ts`, so none of the Step 0.9-incident background jobs run). Covered: self-messaging
and sold/missing-listing rejection on open; idempotent re-open with exactly one message
created; both roles see the right `role` value in their own inbox; unread counts track
who sent the last message and flip correctly after a reply and after marking read;
message pagination ordering (newest-first in the API, as specified); one-sided hide and
its un-hide-on-reply behavior; the snapshot-vs-live title switch exactly at the moment a
listing is removed; the 7-day closed-window boundary for a sold ad; a blocked pair losing
inbox visibility and send ability; and full cursor pagination across a 32-message thread
(30 + 2). Cleaned up all listings, threads, messages, the one block row, and both
temporary users, then confirmed every affected table's row count was unchanged from
before the test.

## Results — all 41 checks passed.
