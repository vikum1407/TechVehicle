# Milestone 1, Step 1.2 (backend) — Post ad — verification

Date: 2026-10-10. Run with `npx ts-node src/scripts/verify1_2_listings.ts` (temporary script,
deleted after this file was written).

## What was built
- `backend/src/routes/mart/listings.ts` — `POST /mart/listings`, behind `requireProfile` +
  `requireRules` (both already existed from Step 0.9/0.11). Exported pure function
  `validateListingCreate(body, r2PublicUrl)` implements every rule in `02-data-model.md`
  §4.1 for both `selling` and `wanted` (title, category/type, condition, make/model against
  the real vehicle catalog, year range, price vs. budget, district, photo count/prefix,
  delivery flag) and returns either `{ok:true, data}` ready for `prisma.martListing.create`
  or `{ok:false, error, code}`. Rate-limited with the existing `checkRateLimit('mart-post', ...)`
  at `MART_RATE_LIMITS.POST_LISTING` (10/hour).
- `backend/src/routes/mart/index.ts` — mounts the new router at `/listings`.

## Decision: built full selling+wanted validation now, even though the build plan scopes
1.2's mobile screen to Selling only
`03-api.md` §4 documents one endpoint contract for both types together, and the validation
rules for `wanted` (budget, optional make) are no harder to write alongside `selling`'s than
to leave as a TODO. Writing it once now avoids reopening this file at Milestone 2 Step 2.1
(Wanted ads) to retrofit rules that are already fully specified today. The mobile Post Ad
screen in this step only ever sends `type: "selling"` — nothing can reach the `wanted`
branch from the app yet. Logged in `DECISIONS-MADE.md`.

## Verification method
- 33 pure-function checks against `validateListingCreate` (no DB): every required-field
  rejection, the make/model catalog check (including the free-text "Other" path capped at
  40 chars), year-range rules, price vs. budget rules for both types (including confirming
  the *other* type's fields are silently ignored/forced, e.g. a `wanted` body's `price` is
  dropped to `null` rather than erroring), district validation, photo count/prefix rules,
  and `makeNorm`/`modelNorm` normalization.
- 2 checks against the real production database: created one real `MartListing` row with a
  clearly-fake, non-colliding `ownerPhone` (`+00000000000-test-1.2`), confirmed its fields
  matched what was sent, deleted it, and confirmed the table's row count was unchanged after
  cleanup. Lower risk than Step 1.1's write test: `MartListing.ownerPhone` is a plain string
  column with no foreign key to `User`, so this never touched the `User` table at all.

## Results — all 35 checks passed.
