# Milestone 1, Step 1.5 (mobile) — Edit via the posting screen — verification

Date: 2026-10-10. No temp script — pure UI/data-wiring code, verified by code read-through
against `04-screens.md` §2's "also used for Edit (same form, prefilled)" and `npx tsc
--noEmit`.

## What was built
- `mobile/src/screens/mart/PostAdScreen.tsx` — new optional `editing` prop
  (`EditingListing`, exported). When present: every field initializes from the existing
  listing (category, condition, vehicle, title, description, price, district, delivery
  toggle, and photos — existing photo URLs are treated as already-uploaded, `uploading:
  false`, no re-upload needed), the header reads "Edit Ad", the submit button reads
  "Save Changes"/"Saving…", and submitting calls the new `api.patchMartListing()`
  instead of `api.postMartListing()`, then calls `onPosted(editing.listingId)` (the
  existing id — nothing new was created). The first-action gate still runs in edit mode
  too, for the same reason it runs on create: if `MART_RULES_VERSION` was bumped since
  the user's last post, §22 says to re-ask before the write goes through.
- `mobile/src/config/api.ts` — `patchMartListing()`.
- `mobile/src/screens/mart/DetailScreen.tsx` — the owner's "Edit" button now calls a new
  `onEdit(detail)` prop instead of the "Coming soon" stub, passing the already-loaded
  detail object straight through (it already has every field `EditingListing` needs).
- `mobile/src/screens/MartNavigator.tsx` — `'postAd'` stack entries can now carry an
  `editing` payload; Detail's `onEdit` pushes one. A successful save (edit or create)
  replaces the `postAd` entry with `detail` either way, so Back lands on whatever opened
  the form, not back inside it.

## Decision (logged in full in `DECISIONS-MADE.md`)
Reserve/Available and Delete are **not** wired into any mobile screen this step, even
though their backend is fully built and verified (`1.5-backend.md`). `04-screens.md` §3's
own "own ad" Detail state only shows Edit and Mark Sold — Reserve/Available/Delete are
specified as "My Ads menus" actions, and My Ads doesn't exist until Step 1.6. Inventing a
UI home for them now that isn't in the design was judged worse than leaving them
reachable-once-1.6-exists, same as several earlier backend-ahead-of-UI pieces this build.

## Verified by hand (code read-through + `tsc`)
- Edit prefill round-trips every field correctly, including the "fits all models"/"fits
  all years" cases (`vehicle` stays `null` when `editing.listing.make` is falsy, matching
  how `VehiclePickerScreen` already represents "no vehicle selected").
- Submitting an edit sends the same body shape `validateListingCreate` expects, matching
  the backend's merge-and-revalidate approach exactly.
- `npx tsc --noEmit`: same 7 pre-existing errors as the established baseline, zero new,
  zero in any Mart file.

## Conclusion
Milestone 1 Step 1.5 is complete (backend §1.5-backend.md + mobile, this file). Next is
Step 1.6 — My Ads + My Mart, which is also where Reserve/Available/Delete finally get a
real place to live in the app.
