# Milestone 1, Step 1.2 (mobile) — Post ad — verification

Date: 2026-10-10. No temp script — pure UI/upload-flow code, verified by code read-through
against `04-screens.md` §2 and §22, plus `npx tsc --noEmit`.

## What was built
- `mobile/src/screens/mart/PostAdScreen.tsx` — the Selling posting form. Runs the real
  first-action gate on mount (`GET /mart/me` → missing name/district shows
  `NameDistrictSheet` → not-yet-accepted rules shows `MartRulesScreen` in `firstAction` mode
  → only then the form) — this is the first real caller of everything built in Step 1.1,
  so the gate components finally get real wiring instead of dev-preview-only triggers.
  Photos (up to 8, horizontal 76px strip, dashed "+Add" tile), Category/Vehicle/District as
  tappable rows that open the Step 1.1 pickers as ad-hoc Modals, Condition segmented
  New/Used, Title, Description, Price, and a native `Switch` for "Can arrange delivery".
  Photos upload one at a time (`api.uploadPhoto(token, uri, 'mart')`, resized to 1280px
  wide at quality 0.7 via `expo-image-manipulator`, matching the existing app-wide pattern
  already used in `AddVehicleScreen`/`ProfileScreen`/etc.) with a per-photo spinner and a
  tap-to-retry overlay on failure. Submit is blocked (inline red errors, not a crash) while
  any photo is still uploading or has an unretried failure, and the rest of the form state
  is kept on a submit failure (error shown as a banner, nothing cleared).
- `mobile/src/config/api.ts` — `uploadPhoto()` gained an optional 3rd parameter
  (`folder?: string`), defaulting to the exact same request body as before when omitted —
  confirmed all 6 existing call sites (`AddVehicleScreen`, `AddServiceRecordScreen`,
  `GarageScreen` ×2, `ProfileScreen`, `VehicleDashboardScreen`) still pass only 2 arguments,
  so their behavior is byte-identical. New `postMartListing()`.
- `mobile/src/screens/MartDevPreviewScreen.tsx` — one new trigger link ("Post Ad screen"),
  same bridge pattern as every other Step 1.1/1.2 piece until Mart Home's real "+" button
  exists (Step 1.3/1.6).

## Decisions (logged in full in `DECISIONS-MADE.md`)
- Selling only — no Selling/Wanted switch (Wanted posting is Milestone 2 Step 2.1; the
  build plan's own global rule says hide/disable entry points for unbuilt steps, and there
  is nothing to meaningfully disable here, so it's simply not rendered yet).
- One combined "Compatible Vehicle" row opens the full 3-step picker built in 1.1, rather
  than 3 separate Make/Model/Year rows as the mockup's literal layout shows — reuses the
  Step 1.1 component as one unit; the spec itself flags this area as a build-time judgment
  call ("decision to confirm at build").
- Camera or gallery, multi-select, via a plain `Alert.alert` action sheet (Take Photo /
  Choose from Library) — cheapest way to satisfy "multi-select from gallery or camera"
  without a new UI component.
- "Can arrange delivery" uses the existing native `Switch` (already used in
  `NotificationPrefsScreen`) rather than building a new pixel-matched 42×24 toggle.
- Simplified error UX: inline red text under each invalid field, but no auto-scroll-to-
  first-error (the mockup's scroll behavior) — would need per-field layout measurement for
  a 10-field form; judged not worth the complexity for a first pass.
- All Mart mobile strings remain plain English (no i18n keys) for now, matching every
  Step 1.1 screen — resolving an apparent conflict between the build plan's global rule
  ("add every string as an i18n key from Milestone 1") and Step 3.7's own description
  ("i18n keys for all Mart text") by treating 3.7 (later, more specific) as the step where
  Mart i18n keys actually get added, same precedence logic `04-screens.md` §23 already
  establishes for itself.

## Verified by hand (code read-through + `tsc`)
- Gate order matches §22: missing profile → sheet; profile present but rules not accepted
  → rules screen; both satisfied → form. `checkGate()` re-runs after each gate step so the
  originally-started action (posting) is never lost, per §22 point 3.
- `uploadPhoto`'s new 3rd parameter is additive: grepped all 6 existing call sites, each
  still calls it with exactly 2 arguments.
- Submit validation covers every required field from `02-data-model.md` §4.1's selling
  rules (photos ≥1 and none pending/failed, category, condition, make, title, price,
  district) — mirrors (not replaces) the authoritative server-side check in
  `validateListingCreate`.
- `npx tsc --noEmit`: same 7 pre-existing errors as Step 1.1's baseline, all in files this
  step never touched. Zero new errors.
