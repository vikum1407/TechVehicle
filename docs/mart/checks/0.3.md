# Step 0.3 — notificationPrefs refactor — verification

Date: 2026-10-07. Run with `npx ts-node src/scripts/verify0_3.ts` (temporary script, deleted after this file was written — logic preserved here).

## What changed
- New file: `backend/src/utils/notificationPrefs.ts` — single shared `NOTIFICATION_PREF_DEFAULTS` + `parsePrefs()`.
- Removed the 6 duplicated local `parsePrefs()` copies and replaced with an import of the shared one, in: `jobs/mileageReminders.ts`, `jobs/renewalReminders.ts`, `jobs/serviceNotifications.ts`, `routes/bookings.ts`, `routes/garages.ts`, `routes/serviceSubmissions.ts`. No other code in these 6 files changed.
- `routes/auth.ts`: `GET /auth/notification-prefs` now uses the shared `parsePrefs()` (was missing `garage_reminder` from its own local defaults). `PUT /auth/notification-prefs` now reads the user's current stored prefs first and **merges** the request body into them, instead of building a brand-new object from a fixed list of 7 named fields and overwriting the stored JSON entirely.
- Added 3 new keys to the shared defaults for later Mart work: `mart_message`, `mart_wanted`, `mart_rating` (all default `true`). Not used by anything yet.

## Why the PUT route needed more than a one-line fix
Tracing the actual bug: the mobile `NotificationPrefsScreen` already sends **all 8** toggle keys (including `garage_reminder`) on every single save — confirmed by reading `handleToggle()` in `mobile/src/screens/NotificationPrefsScreen.tsx`, which sends `{ ...prefs, [key]: value }`, the full current state. The backend route only read 7 of them (no `garage_reminder`) and **replaced** the entire stored JSON with just those 7 — so a user's `garage_reminder` choice was silently discarded on every save, not just missing from one response. Confirmed as a real, user-facing bug: toggling "Garage reminders" in Settings never actually took effect.

## Verification method
No staging environment and no test runner exist in this repo (confirmed), so verification was done as a standalone, database-free script that:
1. Imports the real new `parsePrefs()` from the shared file (not a reimplementation).
2. Re-creates the exact old logic that was deleted (copied verbatim before removal) for direct comparison.
3. Runs both old and new logic against 8 representative inputs (null, undefined, empty string, empty JSON, partial JSON, invalid JSON, and inputs touching `garage_reminder` directly).

## Results — all passed
1. **New shared `parsePrefs()` vs the 5 identical old copies** (mileageReminders, renewalReminders, bookings, serviceNotifications, serviceSubmissions): same output on all 7 common keys, for all 8 inputs. ✅
2. **New shared `parsePrefs()` vs the old `garages.ts` copy** (the one that already included `garage_reminder`): same output on all 8 keys, for all 8 inputs. ✅
3. **`GET /auth/notification-prefs`**: old 7 keys unchanged for every input; new response additionally includes a correct `garage_reminder` value every time (previously absent from the defaults, so sometimes missing from the response). ✅
4. **`PUT /auth/notification-prefs`, normal case**: when given the app's real full-body save pattern, all 6 originally-working keys save identically to before. ✅
5. **The bug, proven**: old PUT's result object has no `garage_reminder` key at all, even when the app sent `garage_reminder: false`. New PUT correctly saves it. ✅
6. **The deeper bug, proven**: simulated a user with prior stored prefs (`garage_reminder: false`) saving an unrelated toggle (`booking`) — old logic's replace-the-whole-object behavior wipes `garage_reminder` from storage even though the user never touched it. New merge logic preserves it (and would preserve future `mart_*` keys the same way, before the app even has UI for them). ✅

## Conclusion
No behavior differs for any of the 7 previously-working keys in any of the 6 refactored files or the GET route. The one intentional behavior change (PUT route) fixes a confirmed real bug without altering how the 6 already-working keys save. Safe to ship as its own isolated commit, per plan — nothing else needed to be touched or re-tested.
