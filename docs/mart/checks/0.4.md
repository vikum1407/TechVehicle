# Step 0.4 — clear dead push tokens — verification

Date: 2026-10-08. Run with `npx ts-node src/scripts/verify0_4.ts` (temporary script, deleted after this file was written).

## What changed
`backend/src/utils/push.ts`: `sendPush()` now reads Expo's push response. If the ticket shows `status: 'error'` with `details.error === 'DeviceNotRegistered'`, it clears that token (`pushToken = null`) for whichever user has it, via `prisma.user.updateMany({ where: { pushToken }, data: { pushToken: null } })`. Added the file's own `PrismaClient` instance (matching the existing per-file convention used everywhere else in the backend).

**No call sites changed.** `sendPush`'s exported signature (`pushToken, title, body, data?`) is unchanged, so all 28 existing call sites across 9 files continue to work exactly as before — this was a deliberate choice to keep the change isolated to one file.

## Verification method
No staging environment exists, so this was tested against the **real** production database, but safely: `sendPush` was called with a fake token (`ExponentPushToken[TEST-FAKE-TOKEN-FOR-0.4-CHECK]`) that cannot match any real user — Expo tokens have a specific generated format no real token would coincidentally equal. The network call to Expo was mocked inside the script's own process only (no real push notification was sent to any device, and the live Render server was untouched — this was a separate local process). This proved the real database write path works end-to-end while guaranteeing zero rows could be affected.

## Results — all passed
1. Sanity check: confirmed zero real users have the fake test token before starting.
2. `DeviceNotRegistered` response → `sendPush` ran the real `updateMany` against production without error, and (as guaranteed by the fake token) zero rows were affected.
3. Normal `ok` response → completes without attempting any token clear.
4. A different error (`MessageRateExceeded`, simulating some other Expo error) → does NOT clear the token — only the specific `DeviceNotRegistered` case does.
5. `null` / malformed token still returns immediately without calling `fetch` at all — unchanged from before.

## Conclusion
The fix is isolated to one file, doesn't change the function's public signature, and doesn't affect any of the 28 existing call sites. Verified against production safely using a token guaranteed not to match real data. Safe to ship as its own isolated commit.
