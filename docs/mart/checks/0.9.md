# Step 0.9 — beta gate, middleware, empty /mart router — verification

Date: 2026-10-08. Run with `npx ts-node src/scripts/verify0_9.ts` (temporary script, deleted after this file was written).

## What was built
- `backend/src/middleware/martGate.ts` — `martGate` (Express middleware, 404 when the caller isn't in `MART_BETA_PHONES`) + `isMartBetaPhone()` (same logic for `GET /app-config`, which has no `req.phoneNumber`).
- `backend/src/middleware/requireProfile.ts`, `requireRules.ts`.
- `backend/src/routes/mart/me.ts` — placeholder `GET /mart/me` (just `{ ok: true }`), `backend/src/routes/mart/index.ts` — the empty `martRouter`.
- `backend/src/index.ts` (existing file, additive edit): new `GET /app-config` route, `app.use('/mart', authMiddleware, martGate, martRouter)`. Nothing existing removed or changed — only new imports and new route registrations added.

## A real bug found and fixed before committing
`martGate`/`isMartBetaPhone` normalized the `MART_BETA_PHONES` list entries before comparing, but not the caller's own phone number — an inconsistency that would only misfire if `req.phoneNumber` ever arrived un-normalized. In practice it always does (the login flow normalizes it before issuing the JWT), so this wouldn't have caused a real incident, but it was a latent fragility worth closing. Fixed by normalizing both sides before comparing. Caught by the verification script itself, not after the fact.

## Verification method
- `martGate` and `isMartBetaPhone` are pure logic — tested directly with fake `req`/`res` objects and `process.env.MART_BETA_PHONES` set/unset, no server and no database involved.
- `requireProfile`/`requireRules` do read the database, but only ever **read** — tested against a real existing user, relying on the fact (confirmed in the Step 0.8 check) that every current user has `displayName`/`district`/`martRulesAcceptedAt` all `null` right now, since nobody has used Mart yet. Zero writes.

## Results — all 10 checks passed (after the fix)
Covers: gate open when unset, allow a listed phone, block an unlisted phone with a 404 (not 403 — looks like the route doesn't exist), list-entry normalization, `/app-config`'s 4 state combinations (gate on/off × token present/absent), and both profile/rules middleware correctly blocking a real user who hasn't completed either step yet.

## What's NOT yet verified — and why, honestly
The build plan's own done-check is phrased as an HTTP-level test ("non-beta phone gets 404 on /mart/me, beta phone gets 200"), which needs a running server and a real JWT. Vikum gave 2 real phone numbers (admin + beta) for this; one didn't have an account yet, so the plan shifted to using 2 existing real users' phones for a logic-level test instead.

**Attempting this surfaced a real incident:** starting the backend locally with `npm run dev` to test one route also starts the full app, including background jobs (`startRenewalReminderJob` etc.) that run their check **once immediately on startup**, confirmed by a comment in `renewalReminders.ts` ("Run once on startup, then every hour"). Since the local `.env` points at the real production database, this meant the real renewal/service/booking/mileage reminder logic ran once against real data during the ~20 seconds the server was up, before being noticed and killed (PID found via `netstat`, force-killed via `taskkill`).

**Confirmed impact, checked the next day (2026-10-09): zero.** Queried `AppNotification` for any row created between 2026-10-08T18:19:30Z and 18:21:30Z (the incident window, widened on both sides) — **0 results.** Nothing was actually sent to anyone. The "already sent today" guard fields almost certainly meant there was nothing new due in that short window anyway. Confirmed with data, not just reasoning.

**Decision: do not attempt a live-server test against production again for this kind of check.** Step 0.9 is treated as verified by the middleware-level tests above instead (10/10 passed, including a real bug found and fixed). The true end-to-end "200 vs 404" proof will happen naturally once Milestone 1 ships real screens and Vikum tests via the actual deployed app on his phone — against the single real Render instance, with no duplicate-job risk.

## Conclusion
Middleware logic and database-reads are fully verified and a real bug was caught and fixed. The live HTTP round-trip is deliberately not attempted locally again, for the reason above — logged as a lesson for any future local-server testing, not a skipped step.
